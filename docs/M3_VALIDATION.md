# M3 validation report: evidence architectures and the end-to-end thin slice

23 Nov 2026. Every figure below was computed by code from saved run files. The files are named in each section and live under `data/` (git-ignored) unless they are in `output/dev/`. The dev-slice dollar figures are a **pipeline test, not a finding**.

## 1. What was built in this session

| Piece | Module | What it guarantees |
|---|---|---|
| Evidence-support scorer | `src/evidence_score.py` (evidence-score-v1.1) | Scores every published stall signal against the frozen yardstick (labels bench-v1 r89, evidence-v1, negative-v1) without changing it. Activity matching reuses the frozen `bench.score`. |
| Grounding packet | `src/packet.py` (packet-v2) | Numbers the sentences of each claim's message as its batch showed it, plus the linked original of each hidden quoted block, with raw-byte offsets. A table message shows its prose lines only. |
| Grounder | `.claude/agents/grounder.md` (grounder-v1), `src/ground.py` | A fenced Haiku agent (Read and Write only) returns supported, unsupported or unsure with sentence ids. **Code** cuts the evidence from the raw file. An invalid or out-of-scope citation is rejected. The grounder never changes the extracted activities. |
| H (evidence last) | schema `extract-v8h`, `verify.check_signal_evidence` | Per-signal quotes are written after classification. Unresolved claims are kept and logged, never dropped silently. |
| J (selective grounding) | `src/selective.py` | Selection uses only H's output, never labels. It is evaluated offline against the approved evidence, never against the grounder's verdicts. |
| Events | `src/events.py` | One event per process per thread. Quoted copies are merged through their `first_seen` anchor, so a quoted text seen in several threads counts once. Copies were already merged at ingest. |
| Synthesis | `.claude/agents/synthesizer.md`, `src/synth.py` | Sonnet reads a compact list (no raw email) and proposes processes and minutes-saved assumptions. Code validates ids, uniqueness, minimum size, minutes range and reasons, and lints numbers in model prose. |
| Scoring | `src/score.py` | Decimal arithmetic at $85/hour, half-up rounding for display only. Every number is a claim record of kind counted, assumption or estimated. Minimum-evidence and window rules apply, overlap is counted once, and `check_chains` proves every chain ends in verified quotes or documented assumptions. |
| Artifact | `.claude/agents/artifact-writer.md`, `src/act.py` | Sonnet drafts a document citing `[Qn]`. Code verifies every citation and appends each quote verbatim with its original file name and byte offsets, re-read from the raw file. |
| Report and dashboard | `src/report.py`, `src/serve.py` | Flask on 127.0.0.1 only. Raw email is escaped and highlighted by byte offsets. Drill-through runs from a $ figure to its formula and labelled inputs, then to events, verified quotes, and the raw email with the quote highlighted. The server can run detached. |
| Pipeline and command | `src/pipeline.py`, `.claude/commands/observe.md`, `src/headless.py` | Stages are cached per batch and stage (input fingerprint + prompt sha256 + model + schema), with up to 2 retries. A failed batch is never marked read. Every model stage is a fenced headless Claude Code session. `/observe` runs unattended with `claude -p "/observe dev"`. |

The fence now covers four agents (extractor, grounder, synthesizer, artifact-writer). Each may read only its own input folder, write only its own staging file and hand back its reply. Every gold file is unreadable to all of them, and a live probe confirmed this for the grounder.

**Counting units (reconciled 23 Nov 2026).** The grounder counts claims (observation × signal). The evidence scorer counts each (labelled activity, signal) once, because duplicate observations of one activity merge into one event downstream, and it also counts each signal published on an observation that matches no labelled activity. Those count toward the denominator and never as correct. So I1's grounder reported 22 published claims, which the scorer counts as 21 (one activity was published by two observations). Likewise I2 17 → 16, I3 24 → 22, J1 23 → 22, J2 24 → 22. An earlier draft of this report wrote precision as "14/16 (+2)", as if the 2 unlabelled ones were extra; they are already inside the 16. In-session and headless "tokens" are different measures (a harness context figure vs the CLI's summed input/output/cache tokens), so costs are compared in seconds and notional dollars only.

## 3. Decision

**Selected for M3 and the working baseline for M4: architecture I**, clean-C extraction (`extract-v8c`) followed by grounding of every claimed stall signal (`grounder-v1`). The user decided this on 23 Nov 2026:

> Let's move forward with **Architecture I (clean-C + grounder)** as our selected configuration for M3 and the working baseline for M4. Keep **H + grounder** fully preserved as our quality benchmark and backup option. … we should only switch if further testing confirms the improvement and demonstrates that it can meet our under-30-minute full-run requirement.

Why I is the default:
- It is the simplest design that meets the provenance rules: one unchanged extraction prompt, an independent semantic check on every published signal, and citations cut by code.
- It can see linked originals for cross-message context.
- Unresolved and rejected claims are recorded, never silently dropped.
- Per benchmark batch it costs $0.067 + about $0.01 notional, against $0.10–0.15 + $0.01 for H, and is 15–20% faster.

**H + grounder is preserved as the quality benchmark and backup.** On this benchmark it published 20 and 21 signals with approved evidence (precision 21/22 both runs), against I's 19, 13 and 20, and its claims were steadier (36/42 vs 33/43 same claimed signals). That is two runs against three, and H's own quotes are discarded once grounded, so the gain comes from steadier extraction claims.

What is kept for it:
- the prompt, committed at `eval/prompts/extract-v8h.md`, with a test that keeps it exactly the active prompt plus the evidence section;
- schema `extract-v8h` and its verifier path, with tests and mutants;
- its runs and scores, in `eval/results/`;
- the switch, documented in `config/settings.yaml`.

A switch needs two things: further tests confirming the gain, and a measured full run under 30 minutes. H alone (no grounder) is not a candidate: it published 2–3 unsupported or false signals per run and weakly evidenced ones.


## 4. Execution feasibility (`eval/results/runtime_estimate.json`)

Measured:

- **4-batch dev concurrency test** (in-session extractor subagents, clean-C, 202 messages): all four started in the same second. Durations were 149, 200, 230 and 420 s; wall time 412 s against 978 s serial; 323/323 quotes verified; no retries.
- **8 headless grounders at once**: all started in the same second; wall 67 s against 286 s summed. One earlier 4-way run showed a 56 s stagger that did not recur.
- **Headless end-to-end** `claude -p "/observe dev"`: 511.6 s wall. That covers one fresh extraction (378 s), its grounding (72 s), synthesis (Sonnet, 31 s, 7 processes), scoring, one artifact (Sonnet, 17 s), the report and a detached server. The orchestrator was Haiku ($0.0075 notional), with 0 permission prompts.
- **Plan meter**: the 4 dev batches plus about ten orchestrator turns used 5% of a fresh 5-hour window and 1 point of the weekly limit.

Full corpus: 49 batches, 1.15 M estimated tokens, about 15.3× the dev slice. A simulated worker pool gives:

| Workers | Mean per-token rate | Pessimistic (slowest dev batch's rate) |
|---|---|---|
| 4 | 76.0 min | 110.9 min |
| 8 | 39.5 min | 58.8 min |
| 12 | **28.9 min** | 42.6 min |
| 16 | **23.5 min** | 34.4 min |

**Conclusion:** the full run fits 30 minutes only with at least 12 parallel sessions at the mean rate. Neither 12-way concurrency on Pro nor the per-mailbox synthesis split has been measured, and the pessimistic case fails even at 16. Budget is feasible: extraction plus grounding is estimated at roughly 35–55% of one fresh 5-hour window and about 15% of the weekly limit.

Levers for M4, in order of expected effect:
1. Measure 12- and 16-way concurrency.
2. Smaller batches (about 12k tokens) to cut the tail.
3. Cut extractor output: Haiku's output is 50–66k tokens per batch against about 25k of JSON, so check thinking and the unused fields (`confidence`, `limitations`).

The M3 measurements do **not** yet show that the 30-minute target is met.

## 5. Dev slice end to end (`output/dev/`)

- **Coverage:** 202/202 slice messages read, each with a disposition: 146 observations, 46 not business, 8 business with no process signal, 2 ambiguous. The ledger page lists all 3,240 files.
- **Grounding:** 303 verified observations carried 90 claimed signals. 78 were published with code-cut evidence, 5 judged unsupported and 7 left unresolved, all recorded.
- **Synthesis:** 7 processes; 228 observations left unassigned as one-offs.
- **Ranked list:** 7 opportunities, running total **$29.25/month** (pipeline test). Rank 1 is "Unallocated or unmatched meter volume resolution": 6 events, 11 emails, 5 threads, 24.06 months observed (farmer-d window), 30 minutes per event assumed (range 15–50), $10.60/month, confidence high.
  - Rates are low on purpose: the denominator is the mailbox's whole window (R7), while the slice holds only a few dozen of its messages.
- **Artifact:** `output/dev/artifacts/P4-checklist.md`, an exception-investigation checklist with 23 verified citations from 7 emails. The numbers-lint flag on its "days 1-20 / 21-31" placeholder example is visible in the run log.
- **Verification (re-run 23 Nov 2026, after the user's decision):**
  - **Cache.** `python -m src.pipeline run --slice dev --offline` refuses any model call. It completed with all 10 model stages (4 extractions, 4 groundings, synthesis, artifact) as cache hits, and rebuilt the dashboard data identical apart from its timestamp. The report rebuilds byte-identically now that batch order is fixed in code. An interrupted run adopts a finished attempt only if its fingerprint, attempt id, prompt hash, schema and confirmed model all match.
  - **Audit.** `tools/audit_dashboard.py dev`: all 431 quotes re-read byte-exact from the raw files; all 64 claims chain to verified quotes or documented assumptions; every opportunity's events per month, hours, dollars and the running total recompute exactly in Decimal from the stored claims; 98 pages load and 114 quote links open the raw email with the quote highlighted. 0 problems.
  - **Race fixed, across processes.** The mutation check's baseline caught a race about once in 20 runs: parallel `finalize` calls could tear or lose `status.json`. The first fix was a thread lock, which protects the pipeline's worker threads but not separate processes, such as an orchestrator running `finalize` from parallel shell calls. The final fix, `src/filelock.py`, combines a thread lock with an OS file lock (`msvcrt` on Windows, `fcntl` elsewhere) around every shared-file write, and writes `status.json` atomically with a retried replace. Tests using real separate processes show:
    - six processes making 240 locked read-modify-writes lose none, and the mutant that locks threads only is caught;
    - a lock held by another process blocks until released;
    - a reader in another process never sees a torn file while a writer rewrites it 150 times, and the plain-write mutant is caught;
    - four processes finalizing concurrently keep `status.json` and the run log whole;
    - a spy test proves `finalize` does all its shared-file work inside the cross-process lock, and the unlocked mutant is caught deterministically. Each mutant was caught 3/3 times when run repeatedly.
- **Tests:** 377 offline tests pass; the mutation check catches **131/131** (28 new rules this session, 3 earlier mutants re-pointed after refactors). Both benchmark checks report 0 problems. The labels, rules, `src/bench.py`, evidence spans, negative claims and `src/evidence_bench.py` all still match their freeze hashes. The holdout was never read.

## 6. Limitations and open items

1. **Runtime: the M4 priority** (user, 23 Nov 2026: full-corpus performance, reliability and scalability; no extractor prompt tuning unless a significant defect is found). The 30-minute target is unproven (section 4). Full-corpus synthesis needs the per-mailbox split (PLAN 3.2), which is not built yet.
2. **Extraction recall drives signal recall.** Escalation was never found; waiting reaches 3–4 of 8; 670#1 correction is missed in every run.
3. **Shared verified path.** `data/extract/verified/` is shared by slices, so a bench run displaced a dev result and forced one re-extraction. Fix in M5 with per-slice folders.
4. **The grounder accepted one negative claim** (670#2 waiting in J2), so it is not infallible. The M6 reviewer stage is still to come.
5. **No reviewer yet.** Claims are shown without review. The artifact threshold is $1,000/month with an M3 "at least one" override: the slice's top opportunity is $10.60.
6. **Quote overlap in artifact packets.** Packets can hold overlapping quotes (an observation's quote inside its evidence sentence). This is harmless but noisy.
7. **1000#1 attribution note.** This remains a review note only: no provenance effect was found, because evidence attribution comes from block headers, not label actors.
